# Hackathon rules checklist

Verified against the official rules and the repository state captured on
2026-07-29.

## Eligibility - participant must confirm

- [ ] Each participant is a legal United States resident and at least 18.
- [ ] Each participant enters as an individual, not on behalf of an employer,
      client, or other entity.
- [ ] No participant is restricted by employment, contract, sanctions, export
      controls, or other applicable policy or law.
- [ ] The sponsor has accepted the participant's registration and required
      documents.
- [ ] A participant belongs to no more than one two-person team.

These are gating conditions. Code quality cannot cure ineligibility.

## Entry requirements

- [x] OpenSearch-related agentic IDE skill.
- [x] Addresses a concrete customer pain point and improves productivity.
- [x] English-language project.
- [x] Apache 2.0 license.
- [x] No proprietary runtime dependency.
- [x] AI assistance is allowed; the participant must actively direct the work.
- [x] Does not reproduce a skill currently in the official repository.
- [ ] Participant must ensure it does not reproduce another hackathon
      submission at submission time.
- [ ] Production-ready code at final submission.
- [ ] Clear README.
- [ ] Video no longer than five minutes.
- [ ] Submit through the official GitHub issue template during the promotion
      period.
- [ ] Do not submit until final: an entry cannot be enhanced after submission.

## Timing

- Promotion opens: approximately July 15, 2026 at 8:00 a.m. Pacific Time.
- Entry deadline: approximately August 17, 2026 at 11:59 p.m. Pacific Time.
- Anticipated judging: August 17-30, 2026.
- Anticipated winners announcement: September 3, 2026.

The official rules control over conflicting landing-page text.

## Judging targets

| Dimension | Weight | Project strategy |
|---|---:|---|
| Technical innovation | 25% | Agent orchestrates capability contracts, non-mutating probes, evidence compilation, negative assertions, and convergence. |
| Community creativity and utility | 25% | Targets a documented, repeated SRE/InfoSec pain and turns it into a reusable workflow primitive. |
| Operational excellence | 20% | Deterministic compiler, no secret persistence, TLS verification, safe defaults, tests, and explicit uncertainty. |
| Vendor neutrality and portability | 15% | Python standard library; OpenSearch Security APIs; no cloud or model vendor dependency. |
| Documentation and enablement | 15% | Lean skill, workflow schema, example, evidence report, README, and demo plan. |
